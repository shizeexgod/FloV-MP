# FloV:MP — план развития веб-платформы

Документ фиксирует направление следующих этапов. FloV:MP позиционируется как
самостоятельный мультиплеер для GTA V: движок, лаунчер, веб-управление,
документация и инструменты владельца проекта.

## Ближайший этап: вход и регистрация

- Вход и создание аккаунта через одноразовый код из письма.
- Пароль как дополнительный способ входа — только после отдельного решения.
- Защищённые HttpOnly-сессии, журнал входов и завершение активных сессий.
- 2FA TOTP через приложение-аутентификатор, резервные коды восстановления.
- Ограничение частоты отправки писем и попыток проверки кода.
- Письма: код входа, новый вход, включение 2FA, восстановление доступа.

### Принципы интерфейса

- Левая навигация по понятным группам, без перегруженной сетки вкладок.
- На первом экране — состояние проекта, серверов и события, требующие внимания.
- Реальные данные вместо демонстрационных счётчиков.
- Опасные операции требуют подтверждения; длительные показывают прогресс.
- Все состояния: загрузка, пустой список, ошибка, отсутствие прав, офлайн.
- Полная русская и английская локализация без смешения языков.

## Backend

- MariaDB как основной источник данных; локальный JSON только для разработки.
- Проектная модель прав: Owner, Administrator, Developer, Viewer.
- Почтовые коды с ограниченным сроком жизни и одноразовым использованием.
- TOTP 2FA, резервные коды, аудит действий и активных сессий.
- Очередь команд игровому агенту: start, stop, restart, broadcast, RCON,
  управление ресурсами.
- Поток консоли и событий в реальном времени с безопасным переподключением.
- Телеметрия серверов, история инцидентов и уведомления.
- API-ключи с областями доступа, ротацией и журналом использования.
- Подписанные пакеты обновлений и проверка целостности файлов.

## EXE-приложение владельца

Отдельное Windows-приложение для управления релизами мультиплеера. Оно не
заменяет игровой лаунчер клиента и не должно содержать секреты в открытом виде.

- Авторизация тем же аккаунтом и подтверждение критических действий через 2FA.
- Создание релиза из выбранной папки и расчёт хэшей файлов.
- Формирование и криптографическая подпись манифеста обновления.
- Загрузка изменённых файлов в CDN-хранилище.
- Каналы Production / Testing с поэтапной публикацией и быстрым откатом.
- История версий, размер патча, прогресс загрузки и журнал ошибок.
- Клиентские лаунчеры скачивают только изменившиеся файлы и проверяют подпись.

## Инфраструктура

- Публичный Next.js-сайт — Vercel.
- MariaDB, агент серверов и длительные realtime-соединения — отдельный backend
  на VDS; не привязывать критичное управление к ограничениям serverless.
- Патчи и FastDL — S3-совместимое хранилище или выделенный CDN.
- Секреты подписи релизов — только на backend, не внутри EXE и не в браузере.
- Наблюдаемость: структурированные логи, метрики, резервные копии и алерты.

## Вопросы для согласования

1. Вход только по коду из письма или код + постоянный пароль?
2. Какой почтовый провайдер использовать: Resend, SMTP Яндекса или другой?
3. 2FA обязательна только владельцам проектов или доступна всем по желанию?
4. EXE-приложение нужно только владельцу FloV:MP или также владельцам проектов?
5. Где хранить патчи: Cloudflare R2, S3, собственный VDS/CDN или иной сервис?
6. Нужны ли каналы обновлений Production / Testing уже в первой версии?
7. Какой способ восстановления аккаунта допустим при потере почты и 2FA?
