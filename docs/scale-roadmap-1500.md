# FloV:MP — дорожная карта на 2000+ онлайн

Цель: устойчивые **2000+** игроков (спрос уже есть: 2000+ потенциальных игроков,
несколько заказчиков), без задержек, краш-фри ≥90%. Документ опирается на уже
существующие компоненты кода — многое из инфраструктуры под масштаб **уже
написано**, но не включено по умолчанию.

## ВАЖНО: 2000+ = горизонтальное масштабирование (не один процесс)
Один процесс alt:V исторически упирается в ~1000–1500 игроков (потоки синхронизации,
CPU, память одного инстанса). **2000+ на одном процессе нереалистично.** Путь на
2000+ = **несколько серверных инстансов** с общей личностью/банами/экономикой —
что идеально ложится на модель лицензии «**до 10 серверов на проект**»
([[flovmp-monetization-license-model]]):
- Игроки распределяются по инстансам (шарды/слои: например, по 1000–1500 на инстанс).
- Общая БД (MariaDB) на проект: аккаунты, баны (HWID/IP/подсеть), экономика — одни на все инстансы.
- Бан на одном инстансе действует на всех (общая таблица `punishments`).
- Портал управляет всеми инстансами проекта (`RemoteServerAgent` + `portal_*`).
- Опционально: маршрутизация игрока на наименее загруженный инстанс при заходе.

Т.е. сначала выжать один инстанс до ~1500 (Фазы A–D ниже), затем — горизонтальная
раскладка на N инстансов с общим состоянием (Фаза E).

## Что уже есть в коде под масштаб (не с нуля)
- `FloVMP.Core.Database.MySqlAccountStore` + `WriteBehindQueue` + `SnapshotManager` — путь ухода от JSON-файлов.
- `FloVMP.Core.Spatial.AdaptiveTickManager` — масштабирование тикрейта сущностей по нагрузке.
- `FloVMP.Core.Spatial.SpatialHashGrid` + `OcclusionCullingService` — пространственное партиционирование/интерес-менеджмент.
- `FloVMP.Core.Sync.DeadReckoningInterpolator` — сглаживание синхронизации движения.
- `FloVMP.Core.Voice.VoiceGridRouter` — маршрутизация голоса по сетке (не всем всех).
- `FloVMP.Core.Licensing.*` — лицензирование/телеметрия (для монетизации-услуги).

## Узкие места сейчас (демо-дефолт НЕ держит 1500)
1. **Персистентность = JSON-файлы + синхронная запись на каждое действие.** Главный стопор. `JsonAccountStore`/`JsonInventoryStore` пишут файл целиком на каждое изменение в главном потоке. При сотнях игроков — фризы и гонки.
2. **Горячие циклы `OnTick` — O(n) по всем игрокам/транспорту** без пространственной фильтрации (HUD, анти-чит, топливо). При 1500 — заметная нагрузка на тик.
3. **Один процесс alt:V** — верхняя граница того, что alt:V исторически держал (~500–1000). 1500 требует тюнинга потоков синхронизации и мощного железа.
4. **Инфраструктура VDS** — 1500 игроков это реальные ядра CPU (потоки SyncSend/SyncReceive/NetworkWorker), RAM и трафик.

## Фазы

### Фаза A — Персистентность (фундамент, без неё дальше нельзя)
- Переключить дефолт `AccountStoreFactory` на `MySqlAccountStore` (env `FLOVMP_DB_*` уже поддержан).
- Инвентарь/состояние игрока → `WriteBehindQueue` (запись в фоне, коалесинг), снапшоты через `SnapshotManager`.
- Схема БД + индексы (`sql/`), пул соединений, ретраи.
- Критерий: 0 синхронных файловых записей в главном потоке; краш сервера теряет ≤ N секунд (окно write-behind), не сессию.

### Фаза B — Горячие пути под нагрузку
- HUD/анти-чит/стриминг обходят игроков через `SpatialHashGrid` (только релевантные), не весь список.
- Включить `AdaptiveTickManager` в реальные системы (дальние/спящие сущности реже).
- `OcclusionCullingService` + интерес-менеджмент: игрок получает синк только ближних сущностей.
- Голос через `VoiceGridRouter` (сетка, не broadcast).
- Критерий: стоимость тика растёт сублинейно к онлайну (не O(n²)).

### Фаза C — Нагрузочный тест (превратить веру в цифры)
- Синтетический load-test: N ботов/симулированных сущностей подключаются, двигаются, стреляют, торгуют.
- Замер: тикрейт сервера, CPU/RAM, задержки синка, БД — при 250 / 500 / 1000 / 1500.
- Найти реальный потолок и первое узкое место, чинить итеративно.
- Критерий: устойчивый тикрейт при 1500 на целевом железе.

### Фаза D — Инфраструктура и эксплуатация
- Сайзинг VDS под целевой онлайн (ядра под sync-потоки, RAM, канал).
- Мониторинг (тикрейт, память, БД, сеть) + алерты; `ServerCrashWatchdog` уже есть.
- Резервное копирование БД, план восстановления.
- (Опц.) HTTPS/TLS на nginx — закрывает MITM для auth/CDN (сейчас HTTP).

### Фаза E — Горизонтальное масштабирование (для 2000+)
- Несколько инстансов alt:V, общая MariaDB на проект (аккаунты/баны/экономика).
- Общие баны через БД (не in-memory `MultiTierBanService`, а таблица `punishments`).
- Портал распределяет/показывает инстансы; `RemoteServerAgent` на каждом.
- (Опц.) балансировка захода на наименее загруженный инстанс.
- Критерий: суммарно 2000+ на N инстансах, бан/личность общие, управление из кабинета.

## Порядок
A → B → C (итеративно с B) → D параллельно → **E для 2000+**. Без A остальное
бессмысленно. Реалистичная оценка до устойчивых ~1500 на инстанс: недели работы +
целевое железо. 2000+ = A–D + горизонталь (E). Путь заложен в архитектуре.
