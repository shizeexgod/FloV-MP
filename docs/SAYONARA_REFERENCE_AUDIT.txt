АУДИТ SAYONARARP КАК РЕФЕРЕНСА ДЛЯ FLOV:MP
Дата: 23.09.2026

Проверенная папка:
C:\SayonaraRP\Sayonara

Цель аудита:
Найти архитектурные решения, форматы данных и игровые контракты, которые
можно самостоятельно реализовать во FloV:MP. Сторонний код и игровые ассеты
не должны копироваться один в один.


1. ОБЩИЙ ВЫВОД

В папке SayonaraRP находится в основном RP-геймод поверх RAGE:MP:

- C#-сервер NeptuneEvo/RedAge;
- клиентский JavaScript;
- CEF-интерфейс;
- база данных и миграции;
- собранный бинарный сервер RAGE:MP.

Исходников сетевого ядра RAGE:MP там нет. Поэтому готовую низкоуровневую
синхронизацию, интерполяцию, хуки GTA или адаптер для Legacy b3889 оттуда
взять нельзя. Полезная часть — архитектура RP-геймода и требования, которые
FloV:MP должен предоставить через публичный API.


2. СЕРВЕРНЫЙ РЕЕСТР ТРАНСПОРТА

В Sayonara автомобиль существует как самостоятельная серверная сущность,
а не как состояние текущего водителя.

Для автомобиля хранятся:

- постоянный SQL ID;
- номерной знак;
- владелец и тип доступа;
- модель;
- здоровье;
- топливо;
- пробег;
- позиция и вращение;
- двигатель и замки;
- двери, поворотники и грязь;
- тюнинг и визуальные компоненты;
- временное runtime-состояние.

Полезные референсы:

C:\SayonaraRP\Sayonara\dotnet\resources\NeptuneEvo\Core\VehicleSync.cs
C:\SayonaraRP\Sayonara\dotnet\resources\NeptuneEvo\Core\Vehicle.cs
C:\SayonaraRP\Sayonara\dotnet\resources\NeptuneEvo\VehicleData\Models\VehicleData.cs
C:\SayonaraRP\Sayonara\dotnet\resources\NeptuneEvo\VehicleData\Models\VehicleCustomization.cs
C:\SayonaraRP\Sayonara\dotnet\resources\NeptuneEvo\VehicleData\LocalData\Models\VehicleLocalData.cs
C:\SayonaraRP\Sayonara\dotnet\resources\NeptuneEvo\VehicleData\LocalData\Models\VehicleLocalStateData.cs
C:\SayonaraRP\Sayonara\database\main.sql

Рекомендуемая архитектура FloV:MP:

VehicleRegistry
  -> PersistentVehicleData
  -> RuntimeVehicleState
  -> ReplicatedVehicleState

PersistentVehicleData хранит данные БД. RuntimeVehicleState содержит
текущего водителя, пассажиров, таймеры и временные флаги.
ReplicatedVehicleState содержит только состояние, которое должны видеть
клиенты.

Это основной ориентир для закрытия пункта 8 roadmap.

Текущий важный пробел FloV:MP: для нативного игрока IPlayer.Vehicle всё ещё
возвращает null:

C:\FloV-MP\server\src\FloVMP.Starter\NativePlayerProxy.cs

Необходимо добавить полноценные сущности транспорта и публичный API:

- CreateVehicle/DeleteVehicle;
- получение машины по постоянному ID;
- водитель и пассажиры;
- вход/выход и смена места;
- двигатель, замки и двери;
- здоровье кузова и двигателя;
- топливо и пробег;
- тюнинг;
- сохранение и восстановление;
- передача управления между клиентами;
- события уничтожения и disconnect водителя.


3. SNAPSHOT И DELTA-СИНХРОНИЗАЦИЯ

Sayonara использует полезную схему:

1. При stream-in клиент получает полный снимок состояния сущности.
2. После этого получает только отдельные изменения.
3. Если сущность вышла из стрима и вернулась, полный снимок применяется
   повторно.

Для транспорта синхронизируются двигатель, замки, двери, бензин, грязь,
поворотники и тюнинг. Для игроков аналогично реплицируются игровые metadata.

Эту схему следует реализовать во FloV:MP для устранения пропадающих машин,
неправильных дверей, сброса ников и рассинхронизации состояния после
повторного stream-in.


4. КАСТОМНЫЕ НИКИ, HP, БРОНЯ И ИКОНКИ

Sayonara полностью отключает штатные nametag'и и рисует собственные:

- имя и ID;
- полосы HP и брони;
- индикатор голоса;
- AFK;
- mute;
- admin/media badges;
- специальные состояния игрока;
- изменение цветов и видимости по metadata.

Референс:

C:\SayonaraRP\Sayonara\src_client\player\gamertag.js

Используемая модель:

- сервер устанавливает replicated metadata;
- при stream-in клиент читает полный набор metadata;
- data handler получает последующие изменения;
- рендерер формирует nametag из этих данных.

Во FloV:MP глобальные nametag-настройки уже существуют, но произвольный
gamemode-контракт пока неполный. SetLocalMetaData нативного клиента сохраняет
значение только в серверном словаре и не реплицирует его остальным игрокам.

Нужно добавить:

- SetSyncedMetaData/GetSyncedMetaData/DeleteSyncedMetaData;
- metadata snapshot при stream-in;
- delta updates;
- клиентский draw hook или декларативную схему nametag;
- настройки отдельных слоёв: name, health, armor, voice и badge;
- API сервера для собственного цвета, шрифта, масштаба и дистанции;
- безопасное ограничение доступных клиенту данных.

После этого владелец сервера сможет менять дизайн ников и HP без изменения
ядра FloV:MP.


5. ЖИЗНЕННЫЙ ЦИКЛ И DISCONNECT

В Sayonara отключение игрока обрабатывается централизованно:

- останавливаются таймеры;
- закрываются сделки и временные интерфейсы;
- очищается голос;
- игрок снимается с транспорта;
- освобождаются арендованные машины;
- удаляются временные объекты;
- сохраняется позиция;
- снимаются привязки к фракциям и организациям;
- очищаются словари активных игроков.

Референс:

C:\SayonaraRP\Sayonara\dotnet\resources\NeptuneEvo\Players\Disconnect\Repository.cs

Во FloV:MP нужен lifecycle-контракт для ресурсов:

- OnPlayerConnecting;
- OnPlayerReady;
- OnPlayerStreamIn/OnPlayerStreamOut;
- OnPlayerEnterVehicle/OnPlayerLeaveVehicle;
- OnPlayerDied;
- OnPlayerDisconnect;
- cleanup scope для таймеров, подписок и временных сущностей.

Это позволит геймодам регистрировать собственную очистку без одного огромного
обработчика.


6. ПРОСТРАНСТВЕННАЯ РАССЫЛКА

Sayonara отправляет события дверей, анимаций, звуков и эффектов только
игрокам в заданном радиусе.

Во FloV:MP стоит предоставить публичный контракт:

EmitInRange(position, radius, dimension, eventName, payload)

Необходимые проверки:

- одинаковое измерение;
- расстояние до сущности;
- существование получателя;
- лимит размера payload;
- допустимое имя события;
- ограничение частоты.


7. БОЕВАЯ СИСТЕМА

Из Sayonara полезны:

- таблица оружия;
- базовый урон каждого оружия;
- множители частей тела;
- отдельные HP и броня;
- износ оружия;
- серийные номера;
- связь оружия с инвентарём.

Референсы:

C:\SayonaraRP\Sayonara\dotnet\resources\NeptuneEvo\Events\CustomDamage.cs
C:\SayonaraRP\Sayonara\dotnet\resources\NeptuneEvo\Core\WeaponRepository.cs
C:\SayonaraRP\Sayonara\src_client\player\damage\index.js
C:\SayonaraRP\Sayonara\src_client\player\weapon.js

Саму модель доверия переносить нельзя. В Sayonara значительная часть урона
рассчитывается клиентом:

- входящий урон игрока применяет клиент жертвы;
- урон питомцам приходит от клиента готовым числом;
- количество выстрелов для износа сообщает клиент;
- часть защитных условий проверяется только клиентским JS.

Во FloV:MP сервер должен быть владельцем combat ledger и проверять:

- существование стрелка и жертвы;
- одинаковое измерение;
- дистанцию;
- текущее оружие;
- наличие оружия и патронов;
- темп стрельбы;
- направление и разумность попадания;
- безопасную зону и god mode;
- повторные/дублированные HIT;
- конечное изменение HP и брони;
- убийцу и причину смерти.

Клиент может сообщать о кандидате на попадание, но не должен назначать
окончательный урон.


8. НАЙДЕННЫЕ УЯЗВИМОСТИ И АНТИ-ПАТТЕРНЫ SAYONARA

8.1. Пробег транспорта

Клиент рассчитывает пройденное расстояние и отправляет centimeters серверу.
Сервер не проверяет отрицательное значение и преобразует его в uint. Это
может создать огромное значение пробега.

Файлы:

C:\SayonaraRP\Sayonara\src_client\vehicle\mileage.js
C:\SayonaraRP\Sayonara\dotnet\resources\NeptuneEvo\Core\VehicleSync.cs

Во FloV:MP пробег нужно считать по подтверждённым сервером позициям с лимитом
скорости и временного интервала.

8.2. Клиентский урон

Некоторые RemoteEvent принимают от клиента готовый damage. Это нельзя
использовать в FloV:MP.

8.3. Износ оружия

Клиент сообщает count выстрелов. Сервер должен сопоставлять его с допустимой
скорострельностью и собственным состоянием боезапаса.

8.4. God-классы

Vehicle.cs содержит почти две тысячи строк и смешивает хранение, игровой
процесс, команды, БД и сетевые события. Во FloV:MP это следует разделить на
Registry, Persistence, Authority, Replication и Public API.

8.5. Широкие catch

Во многих местах ошибка только записывается в лог, после чего состояние может
остаться частично изменённым. Для важных операций нужны транзакции и явный
rollback.

8.6. Дубли и устаревшие файлы

Обнаружены файлы вроде:

- gamertag copy.js;
- sounds copy.js;
- sounds copy 2.js;
- sit1asdas.js.

Их нельзя считать актуальными референсами.

8.7. Неодинаковая серверная валидация RemoteEvent

Часть событий проверяет расстояние и состояние игрока, часть доверяет данным
клиента. Во FloV:MP нужен единый validation pipeline для каждого клиентского
события.


9. МОДЫ И КАРТЫ

В Sayonara обнаружена папка:

C:\SayonaraRP\Sayonara\client_packages\game_resources

В ней есть gameconfig.xml, текстуры, Scaleform RPF и файл dlcpacks.txt с
ручной внешней ссылкой. Полноценного безопасного установщика модов, манифеста,
системы версий и rollback в проекте нет.

Следовательно, Sayonara не закрывает пункт 4 roadmap FloV:MP. Сторонние
игровые ассеты также нельзя автоматически включать в дистрибутив FloV:MP.

Во FloV:MP уже существует:

C:\FloV-MP\server\src\FloVMP.Core\Streaming\AssetStreamingManager.cs

Но на текущем этапе это только in-memory каталог чанков, зон и расчёт
необходимых файлов. Для полноценной доставки ресурсов нужен контур:

сборка ресурса
  -> подписанный manifest
  -> CDN
  -> докачка чанками
  -> SHA-256/подпись
  -> локальный cache
  -> атомарная установка
  -> подключение DLC/карты
  -> rollback


10. ЧТО НЕЛЬЗЯ ПОЛУЧИТЬ ИЗ SAYONARA

В папке отсутствуют исходники внутреннего сетевого движка RAGE:MP. Поэтому
там нельзя найти готовую реализацию:

- сетевой интерполяции игроков;
- ownership migration транспорта;
- entity streamer RAGE:MP;
- хуков GTA b3889;
- нативного адаптера;
- протокола синхронизации ядра;
- серверного сетевого транспорта RAGE:MP.

ragemp-server.exe — собранный сторонний бинарник, а не исходный код. Его не
следует встраивать, перепаковывать или использовать как основу FloV:MP.


11. ПРИОРИТЕТНЫЙ ПЛАН ПРИМЕНЕНИЯ В FLOV:MP

Приоритет 1. VehicleRegistry

- постоянные ID транспорта;
- независимое от водителя состояние;
- водитель и пассажиры;
- серверное владение двигателем, замками, дверями и здоровьем;
- сохранение в БД.

Приоритет 2. Snapshot/delta replication

- полный снимок при stream-in;
- последовательные версии состояния;
- отдельные deltas;
- повторный snapshot после потери последовательности.

Приоритет 3. Публичный vehicle API для геймодов

- CreateVehicle/DeleteVehicle;
- Vehicle entity вместо null;
- события входа/выхода;
- управление состоянием;
- настройка тюнинга.

Приоритет 4. Synced metadata

- metadata игрока и транспорта;
- stream-in snapshot;
- delta updates;
- API кастомных ников, HP, брони и иконок.

Приоритет 5. Серверный combat ledger

- сервер назначает урон;
- проверяет оружие, дистанцию и частоту;
- хранит HP/броню;
- фиксирует убийцу;
- отклоняет поддельные и повторные HIT.

Приоритет 6. Lifecycle и cleanup

- единые события подключения и отключения;
- автоматическая отмена таймеров;
- освобождение сущностей;
- сохранение состояния.

Приоритет 7. Доставка ресурсов

- подписанный манифест;
- безопасный CDN;
- докачка и cache;
- атомарная установка;
- откат при ошибке.


12. ИТОГ ПО ROADMAP

Пункт 4 — раздача модов и карт:

Sayonara не содержит готового решения. Она подтверждает только ожидаемую
структуру game_resources. Для FloV:MP всё ещё требуется собственный pipeline
сборки, подписи, CDN, установки и rollback.

Пункт 8 — владение транспортом на сервере:

Sayonara содержит хороший архитектурный референс. Его можно реализовать
самостоятельно во FloV:MP без копирования исходного кода. Главные элементы:
постоянный реестр, разделение persistent/runtime/replicated state, полный
snapshot при stream-in и серверное владение критическими полями.
