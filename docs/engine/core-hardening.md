# Устойчивость MP-ядра (задача #17)

Обновлено: 2026-08-28
Решение владельца: сначала довести ядро до идеала, потом переносить геймплей Florida V.

## Раунд 1 (2026-08-28) — сделано

### Изоляция исключений на границе с alt:V

`Safe.Run(where, action)` — все наши обработчики событий движка обёрнуты:
исключение (кривой пакет от клиента, баг в одной системе) логируется через
`Alt.LogError` и глотается, не роняя диспетчер событий и сервер.

Обёрнуто: `AuthSystem` (OnConnect/OnDisconnect/OnLogin/OnRegister),
`InventorySystem` (OnAuthed/OnDisconnect/OnMove/OnDrop/OnUse/SaveAll),
`ChatSystem` (OnPlayerAuthed/OnDisconnect/OnSay), `HudSystem` (OnAuthed/Tick),
`GamemodeResource` (OnPlayerAuthed/OnPlayerDisconnect/OnServerStarted/
OnStop.flush/autosave).

### Баг: порядок обработчиков OnPlayerDisconnect

Обработчики multicast-события идут по порядку подписки. `AuthSystem`
подписан первым и на disconnect чистил `_authed` — после чего
`InventorySystem` и `ChatSystem` не могли получить аккаунт игрока
(`_accountOf` → null) → **инвентарь не сохранялся при выходе**.

Фикс: обе системы больше не зависят от `AuthSystem` на disconnect.
`InventorySystem._live` хранит `(Inventory, accountId)`; `ChatSystem._names`
хранит снимок ника. Свои данные — свой источник истины.

### Один аккаунт — один сеанс

`AuthSystem._activeAccounts` (`accountId → playerId`). Вход отклоняется
(`"аккаунт уже в игре"`), если аккаунт уже за другим игроком. Снимается на
disconnect строго для своей записи (`TryRemove(KeyValuePair)`), без гонки с
переподключением.

Зачем: раньше два клиента с одним аккаунтом получали два `_live`-инвентаря
на один `accountId` → last-writer-wins, потеря предметов.

### Сохранность данных

- **Автосейв** всех живых инвентарей раз в 60 с (аккумулятор в `OnTick`).
- **Флаш при остановке** ресурса: `OnStop` → `_inv.SaveAll()`.
- **Карантин битого хранилища**: `StoreFiles.QuarantineCorrupt` —
  повреждённый `accounts.json` / `inventories.json` переименовывается в
  `*.corrupt-<utcTicks>` (не теряется и не затирается молча), сервер
  стартует с пустого. Раньше следующий Save затирал битый файл.

### Мелочи

- `PlayerLifecycle._spawnCounter` → `Interlocked.Increment` (гонка при
  одновременном спавне двух игроков).

### Тесты

`server/tests/FloVMP.Core.Tests` — +3 (`StoreRobustnessTests`): карантин
битого файла для обоих сторов, валидный ре-reload после карантина. Итого 40.

## Раунд 2 (2026-08-28) — сделано

### Хендшейк «клиент готов»

Раньше сервер слал `flovmp:auth:show` прямо в `OnPlayerConnect`. Если
клиентский ресурс ещё не догрузился — событие терялось, игрок навсегда на
чёрном экране.

Теперь: `OnConnect` только логирует; клиент на `connectionComplete` шлёт
`flovmp:client:ready`; сервер (`AuthSystem.OnClientReady`) в ответ шлёт
`auth:show` (если игрок ещё не вошёл). Идемпотентно.

### HUD шлёт только изменения

`HudSystem._lastSent` — последний отправленный кадр на игрока. Если
`(hp, armor, cash, online, hour, minute)` не изменился — `hud:tick` не
отправляется. При стабильном состоянии трафик HUD ≈ 0 вместо 1 пакет/с
на игрока.

### Чистка троттл-словаря

`AuthService.PruneAttempts()` вызывается в начале каждого `Login` —
выкидывает записи старше окна. Словарь больше не растёт от разовых
неудачных попыток с уникальных IP. +1 тест.

### Команды серверной консоли

`ConsoleCommands` (`Alt.OnConsoleCommand`): `saveall`, `online`,
`say <текст>`, `kick <ник> [причина]` — для владельца во время
теста/эксплуатации.

## Открыто (следующие раунды)

- **Нагрузочная модель.** Пока — архитектура без блокирующих вызовов и
  O(n²). Настоящий стресс на 1500–3000 — отдельная веха ПОСЛЕ решения
  «остаёмся на своём» (честная оговорка из CLAUDE.md).
- `HudSystem.Tick` шлёт `hud:tick` каждому каждую секунду безусловно —
  при росте онлайна差 стоит слать только дельты / реже неизменное.
- `AuthService._attempts` — троттл-словарь без периодической чистки (утечка
  одной записи на никогда-не-вернувшийся IP). Добавить sweep или TTL-кап.
- Валидация версии протокола клиент↔сервер (сейчас клиент может слать любые
  события; проверки есть точечно, единого хендшейка нет).
- Watchdog самого `altv-server.exe` (перезапуск при падении) — на уровне
  лаунчера/хостинга, не геймода.
- Игровое время/погода, синхронизация мира.
- Нагрузочный смоук: бот-клиент, симулирующий N подключений (после живого
  теста, когда протокол устаканится).
